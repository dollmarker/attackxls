# 原理详解：附件里「看不见的那一层数据」

> 配套 [`README.md`](../README.md) 阅读。本文只讲**为什么**，不复述怎么用。

---

## 0. 问题的本质

数据在 Excel 文件里至少有四种"存在形态"，而经办人的脱敏操作通常只作用于第一种：

| 层 | 形态 | 用户看得到吗 | 删列 / 另存时会被清理吗 |
|---|---|---|---|
| 渲染层 | 单元格、工作表正文 | ✅ 看得到 | ✅ 会 |
| 缓存层 | `xl/externalLinks/*.xml` 外部数据快照 | ❌ | ❌ **不会** |
| 结构层 | 隐藏工作表、批注、自定义属性、修订记录 | ❌ | ❌ |
| 容器层 | OLE2 扇区残留、二进制残留 | ❌ | ❌ |

**经办人的真实操作序列**：打开台账 → 删掉不想公开的列 → 另存为 → 上传公示页。

这个序列**只影响渲染层**。其余三层原封不动跟着文件上了公网。

## 1. `.xlsx`：本质是一个 zip

### 1.1 结构地图

```
公示附件.xlsx  (zip)
├── [Content_Types].xml
├── _rels/.rels
├── docProps/
│   ├── core.xml            ← dc:creator / cp:lastModifiedBy     🟠 制表人、机器名
│   ├── app.xml             ← Application / Company
│   └── custom.xml          ← 🟠 自定义属性（见过整列塞进去的）
├── xl/
│   ├── workbook.xml        ← <sheet state="hidden|veryHidden">  🔴 隐藏表
│   ├── sharedStrings.xml   ← 正文用到的字符串（已脱敏的那部分）
│   ├── worksheets/sheet1.xml
│   ├── externalLinks/                                           🔴🔴 核心
│   │   ├── externalLink1.xml
│   │   └── _rels/externalLink1.xml.rels  ← 🟠 源台账的落盘路径
│   ├── connections.xml / queryTables/    ← 🟠 数据连接定义、源库 SQL
│   ├── comments*.xml / threadedComments/ ← 🟠 批注
│   └── vbaProject.bin                    ← 🟠 宏里硬编码的数据
```

### 1.2 核心：外部链接缓存（externalLinks）

**怎么产生的**：台账里用了 `数据 → 查询与连接 / 外部链接`，或某个公式引用了另一个工作簿。
Excel 读入源表后会把读到的值**缓存**进文件，以便下次打开时不必重新读源文件。

**关键性质**：这份缓存是**源表读取时的字符串快照**，与"正文里现在还剩哪几列"**毫无关系**。
删列、隐藏列、把列宽调成 0 —— 都不会碰它。

`xl/externalLinks/externalLink1.xml` 的结构：

```xml
<externalLink xmlns="http://schemas.openxmlformats.org/spreadsheetml/2006/main">
  <externalBook r:id="rId1">
    <sheetNames><sheetName val="Sheet1"/></sheetNames>
    <sheetDataSet><sheetData sheetId="0">
      <row r="1">
        <cell r="A1" t="str"><v>毕业生姓名</v></cell>
        <cell r="B1" t="str"><v>学号</v></cell>
        <cell r="D1" t="str"><v>身份证号码</v></cell>
        <!-- … -->
      </row>
      <row r="812">
        <cell r="D812" t="str"><v>4xxxxxxxxxxxxxxx7</v></cell>
        <!-- … -->
      </row>
```

解析方式就是：`zipfile` 打开 → 读该 entry → 按 `<row>` / `<cell r="D812">` 取值。

**它为什么最值钱**：正文可能只有 6 列（姓名 / 学号 / 学院 / 专业 / 班级 / 金额），
而缓存里是 13 列的源台账（+ 身份证号、手机号、开户行、银行账号、家庭住址……）。
一次匿名 GET，上千人的完整档案。

**为什么必须定高危**：不需要登录、不需要绕过任何鉴权、数据往往已被搜索引擎收录、且长期在线。

### 1.3 顺手捡到的附加证据

`xl/externalLinks/_rels/externalLink1.xml.rels`：

```xml
<Relationship Id="rId1" Type="…/externalLinkPath"
  Target="file:///C:/Users/xxx/Desktop/（公示总表1557人)附件2：…汇总表.xlsx"
  TargetMode="External"/>
```

这条**不是数据，是证据**：它暴露了源台账的文件名，甚至制表人的磁盘路径 / 用户名。
写进报告，可以直接证明"该附件是由内部台账另存而来"，而不是巧合。

`docProps/core.xml` 同理：

```xml
<dc:creator>Lenovo</dc:creator>
<cp:lastModifiedBy>信息化管理中心</cp:lastModifiedBy>
```

制表机器名 + 内设机构名，同样可以作为报告里的佐证。

### 1.4 隐藏工作表

`xl/workbook.xml`：

```xml
<sheets>
  <sheet name="公示表"   sheetId="1" r:id="rId1"/>
  <sheet name="全量台账" sheetId="2" state="veryHidden" r:id="rId2"/>
</sheets>
```

`state="hidden"` 在 Excel 里右键「取消隐藏」就能看到；`veryHidden` 只能靠 VBA 或改 XML 才显示。
公示附件里常见「Sheet1 是脱敏后的 6 列，Sheet2 是 veryHidden 的 13 列全量」。

### 1.5 其它常被忽略的位置

| 位置 | 内容 |
|---|---|
| `xl/comments*.xml`、`xl/threadedComments/` | 批注里常有"这个学生的身份证核对过""金额少发了 200" |
| `docProps/custom.xml` | 自定义属性 |
| `xl/connections.xml`、`xl/queryTables/` | 数据连接定义，可能含源库地址与 SQL |
| `xl/vbaProject.bin` | 宏里硬编码的台账数据（按 UTF-16LE + latin-1 双解码扫） |
| `word/*.xml` 里的 `w:ins` / `w:del` | `.docx` 修订模式下"删掉"的身份证号仍完整保留在 XML 里 |

## 2. `.xls`：OLE2 复合文档

老式 `.xls` 没有 externalLinks 这一说，但**裸字符串照样可读**，而且更隐蔽。

### 2.1 容器

文件头魔数 `D0 CF 11 E0 A1 B1 1A E1` —— 这是 CFB（Compound File Binary）格式，
即 OLE2 复合文档。可以理解成"文件系统里的文件系统"：内部按扇区（512 / 4096 字节）分配，
有一张 FAT 表 + 目录项（Directory Entry）描述各个"流"（stream）。

用 `olefile` 列目录即可看到内部流：

```
wxpoly.xls → Workbook 流 407801 字节
haue.xls   → Workbook 流 169378 字节
```

### 2.2 Workbook 流 = BIFF8 记录序列

`Workbook` 流内部是**一串 BIFF8 记录**，每条记录结构固定：

```
[类型 2 字节 LE][长度 2 字节 LE][数据 …]
```

其中最关键的是 **SST 记录（类型 `0x00FC`）** —— Shared String Table，
BIFF8 版的"共享字符串表"，作用等价于 xlsx 里的 `sharedStrings.xml`。
**工作表里出现过的所有文本，都会在这里留一份。**

所以哪怕工作表被删、被隐藏、行被隐藏 —— 只要字符串进过 SST，它就在流里。

### 2.3 为什么"拿正则扫原始字节"会漏

两个原因：

1. **字符串是分片存储的**：BIFF8 的字符串有压缩 / 非压缩两种编码（每字符 1 或 2 字节），
   还有跨 CONTINUE 记录续写的情况。原始字节里，一个身份证号可能被拆成不连续的两段，
   中间夹着长度头 —— 裸正则扫字节会漏。
2. **编码不固定**：`latin-1` / `gb18030` / `utf-16-le` 混着来，单一解码必然漏一部分。

**所以没有任何单一路径是完备的**，必须三路取并集（见 2.4）：

| 路径 | 捞到什么 | 单独用会漏什么 |
|---|---|---|
| 裸字节扫描（ASCII + UTF-16LE 双路） | 文本型号码 | 数字型号码 |
| `xlrd` 逐单元格 | 数字型号码（在 BIFF 里是 IEEE double，字节流里根本没有数字字符） | 非单元格载体里的数据 |
| BIFF 记录级扫描 | 非单元格载体（`0x005A` 等） | — |

`att_pii_scan.py` 在 `xlrd` 可用时走逐单元格解析，不可用时才退化为多编码裸扫 ——
并且会明确标注"结果为下限"，不允许把下限当成"没有"。
`xls.py` 则三路都做，用于把数据完整还原。

### 2.4 非单元格载体：BIFF 记录 `0x005A`（Crn）

**这是本项目最有价值的一条实测发现。**

某些 `.xls`（业务系统导出后经 WPS 转存）会把**整份名册**塞在 BIFF 记录 `0x005A`（MS-XLS 里的 Crn 记录）里，
而工作表里根本没有"身份证号"这一列。`xlrd` / `openpyxl` **一律看不见**这类载荷 ——
只按单元格导出就会**静默丢数据**，症状是"号码清单里有 215 个，导出的 xlsx 里却找不到身份证列"。

Crn 载荷的头部布局（实测）：

```
[colLast 1B][colFirst 1B][rw 2B]   后面接字段体
```

字段体每条是 `[tag 1B][len 2B][grbit 1B][数据]`，三个坑：

1. **`grbit` 是 BIFF8 压缩标志，不是"空字段"标志**
   - `grbit & 1 == 1` → UTF-16LE，占 `len*2` 字节（中文姓名 / 民族 / 住址）
   - `grbit & 1 == 0` → 单字节压缩存储，占 `len` 字节（纯数字的身份证 / 考生号 / 学号）

   ★ 老实现把 `grbit == 0` 当成空字符串，**把压缩存储的那几列整列丢掉** —— 121 个号码一个都读不出来。
   **只有 `len == 0` 才是真·空字段。**

2. **字段多的行会被 Excel 拆成多条 Crn 记录，共用同一个 `rw`**
   实测第 100 行 = `(colFirst=0, colLast=5)` + `(colFirst=7, colLast=7)`。
   必须**按 `rw` 归并、按 `colFirst` / `colLast` 定位列**，否则不是丢行就是串列。

3. **字段之间可能夹对齐填充字节**
   实测有行在字段间夹 5 字节填充（如序号 66），需要在有界窗口内重新找对齐点
   （`xls.py` 的 `_crn_resync`，上限 24 字节），否则整行丢失。

`xls.py` 完整实现了上述解码，并在输出里给出「单元格 vs 非单元格」的载体对照。

## 3. 判定算法

### 3.1 身份证号（GB 11643-1999 / ISO 7064 MOD 11-2）

18 位 = 6 位行政区划码 + 8 位出生日期 + 3 位顺序码 + 1 位校验码。

```python
W  = [7, 9, 10, 5, 8, 4, 2, 1, 6, 3, 7, 9, 10, 5, 8, 4, 2]   # 权重
CK = "10X98765432"                                            # 校验码表

s = sum(int(n[i]) * W[i] for i in range(17)) % 11
校验码 = CK[s]
```

权重的来源：`W[i] = 2^(17-i) mod 11`（i 从 0 计），即 2 的幂对 11 取模。

**为什么"校验位通过率"是数据真实性最硬的指标**：
随机 17 位数字算出的校验码，只有约 1/11 ≈ 9.1% 的概率等于随机给出的第 18 位。
所以一份数据里 1608 个 18 位数字**全部**通过校验位，几乎不可能是伪造或占位符 ——
这是可以直接写进报告的技术事实。

但反过来，**只靠校验位不够**，还要叠加：

- 前 2 位在合法行政区划码集合内（11–15 / 21–23 / 31–37 / 41–46 / 50–54 / 61–65 / 71 / 81 / 82）
- 出生日期是真实日期（月 1–12、日 1–31），年份在合理区间

### 3.2 银行卡（Luhn / MOD 10）

```python
def luhn(s):
    tot = 0
    for i, ch in enumerate(reversed(s)):
        n = int(ch)
        if i % 2 == 1:            # 从右数第 2、4、6… 位
            n *= 2
            if n > 9:
                n -= 9
        tot += n
    return tot % 10 == 0
```

叠加 BIN 前缀（银联 62、以及 4 / 5 / 3x 等）+ 长度 16–19 位，才判定为"严口径"银行卡。

**必须显式挡掉两类误判**：

- 带 `X` 的身份证号本身
- 身份证号被截断后剩下的 17 位纯数字片段
  （否则 `11010519491231002X` 的前 17 位会被当成一个 17 位银行卡号）

### 3.3 掩码识别

`4521242003****2127`、`139****2222`、`6212***********5371` 这类形态**单独计数**，
不与完整号码混计，报告里写明"已脱敏"。**掩码本身不算泄露。**

## 4. 误报的五个来源

每一个都对应一次实测踩坑。

### 4.1 列语义 vs 全文口径

**问题**：全文正则统计会把"非身份证列里的 18 位数字"算进去。
某表 H 列是「毕业生开户银行账号」，里面出现 18 位数字 —— 形状和身份证一模一样；
而随机数字串本身就有约 1/11 的概率偶然满足校验位方程。
**只靠正则 + 校验位无法排除这一类污染。**

**对策**：按「表头 → 列」的语义统计。先定位表头行（前 5 行里非空单元格最多的那一行），
找到表头含「身份证 / 证件号 / 公民身份」的列，**只数这一列**的行数，作为报告数字。
全文口径只作交叉验证，并在报告里注明两个数字的差异原因。

### 4.2 XML 实体未反转义 → 少计 1 条

真实案例里有一条身份证号写成：

```xml
<v>469022200507170323&#10;</v>
```

`&#10;` 是换行符的 XML 实体。只做 `strip()` 不做 `html.unescape()`，
`re.fullmatch` 判定就会失败 —— 统计出来是 1607，真值是 **1608**。

差 1、差 2 这种数字在 SRC 复核时最致命：复核方一验就能推翻整份报告。
**对策**：取值前一律 `html.unescape()`。

### 4.3 身份证号截断片段被误判成银行卡

见 3.2 末段。**对策**：任何 15–20 位纯数字，若它是某个已识别身份证号的子串或前缀，直接排除。

### 4.4 住址识别是启发式

正则（`省|自治区|特别行政区` + 结尾 `号|村|路|街|室|小区…`）会把
「中国银行海南省陵水文教路」这类**行名**当成家庭住址。
**对策**：住址数字在报告里标为"启发式，仅作下限参考"，人工过一遍再写进报告。

### 4.5 数值格式丢精度

身份证号若在原文件里是**数值格式**（不是文本），Excel 只保留 15 位有效数字，
超出部分**在保存那一刻就已经变成 0**。任何工具都无法还原 ——
这是文件的原生缺陷，不是解析问题。报告里遇到"尾数全是 0"的号码，应说明这一点。

## 5. 负结果的证据力分级

"没找到"有两种，混为一谈就是另一种误报 —— **把没查过的地方说成查过了**。

| 级别 | 条件 | 报告措辞 |
|---|---|---|
| **强负结果** | 对**现行站点**做全量审计：页面 + 全部附件 + 两种解析路径（zip 型 / OLE 逐单元格） | 可写"未发现" |
| **弱负结果** | 结论依赖**第三方归档源**，且该源对目标存在系统性零覆盖 | 只能写"源侧无数据"，**不得写"已排除"** |

**判据：先证明覆盖度，再决定负结果强度。**
查归档源时先问：该源归档了目标多少 URL？有没有文档类附件？
若答案是"0 行"，那这个源根本没看过目标，它的"没有"毫无证据力。

> 实测教训：某站经 archive.org 核查为 0 命中，看似干净；但深查发现 archive.org 对该站的
> 公示栏目（`/xsc/`、`/rsc/`、`/attachment/`、`/upload/`）**全部 0 行归档**，
> 而搜索引擎的历史命中证明那些页面确实存在过。故结论只能是弱负结果。

**多源不等于独立源**：宣称"多源交叉验证"前，先验证每个源真的抓到了内容（取一条记录看 HTTP 状态）。
实测中 CommonCrawl 与 archive.org 对同一目标同时零覆盖，根因是目标站 WAF 拒绝归档爬虫 ——
用 WARC 取证坐实（取到的是一条 403 拦截页，署名"统一资源发布与管理系统"、原因"非法的 UserAgent"）。
此时"多源"只是同一盲区被数了一遍。

## 6. 扫描器的四个静默失效点

负结果可信的前提是**扫描器真的读到了内容**。以下四处会导致"扫了但没读到"，而且**不报错**：

1. **gzip 未透明解压** —— 直接扫原始字节会漏读 gzip 响应。实测某快照 raw 5911 字节、
   解压后 26757 字符：直接扫原始字节等于没扫。
2. **OLE 老格式只做字节扫描** —— 数字型号码在 BIFF 里是 IEEE double，字节流里根本没有数字字符，
   必须用 `xlrd` 逐单元格才看得见。
3. **只读单元格** —— 漏掉 `0x005A` 等非单元格载体里的数据（见 2.4）。这是最隐蔽的一种：
   工具不报错、表格看着正常，只是**数字对不上**（号码清单 215 个，导出的表里却找不到那一列）。
4. **XML 实体未 unescape** —— 见 4.2。

**对策：先做正 / 负对照自检。** 喂一个合成的合法身份证号（应通过）+ 一个错校验位的号码（应被拒），
确认校验器工作正常，再下负结论。

## 7. 修复建议的原理依据

**为什么"打码"不是修复**：脱敏打在渲染层，缓存层原封不动。正确做法是**换发布方式**：

1. 公示用的 Excel **另存为新文件**：`数据 → 查询与连接` 里删除全部外部链接与缓存，
   删除隐藏工作表，`文件 → 信息 → 检查文档` 清理自定义属性 / 批注 / 修订记录
2. 公示材料只保留**姓名 + 学号后四位**（或更少）；身份证号、银行账号、手机号、家庭住址一律不出现
3. 对站点 `attachment` 目录做一次**全量排查**（这类文件往往不止一份）
4. 建立发布前检查：公示附件统一由信息中心用脱敏模板生成，**禁止用原始台账直接另存上传**
5. 已泄露的数据不可撤回 → 建议对受影响人群做风险提示，并评估是否需要上报

## 8. 附：dork 家族与归档源

**引擎现实**：360（`www.so.com`）是国内 edu 站唯一稳定的 dork 引擎（`site:` 生效、结果带真实 URL）；
**不支持**子域级 `site:` 与 `filetype:`（`site:根域` 天然覆盖子域）。

```
site:{根域} 补贴 (公示 OR 名单) 表
site:{根域} (助学金 OR 奖学金 OR 资助) 名单
site:{根域} (花名册 OR 汇总表 OR 登记表 OR 发放表)
site:{根域} 拟录取 公示
site:{根域} (求职补贴 OR 就业补贴 OR 困难补助)
site:{根域} ("身份证" OR "身份证号") 名单
```
